# Sandbox mode

This page is the operational summary the playbook and the configurator
should read.

## Selecting the mode

- **Default is PRODUCTION.** An install with `BANKFEED_EB_ENVIRONMENT`
  unset (or empty) runs the production world. Sandbox is chosen ONLY
  when the operator explicitly asks for it at install time — "install
  the finance specialist, **sandbox**" — and the configurator then sets
  `BANKFEED_EB_ENVIRONMENT=SANDBOX` in `plugin-env.conf`, next to
  `BANKFEED_OP_VAULT`. The name is unchanged by issue #4: only the two
  setup-provisioned credentials were renamed.
- **Leaving it unset stays safe under casa's env-readiness gate**
  (issue #4, casa v0.155.0): `.mcp.json` references the variable as
  `${BANKFEED_EB_ENVIRONMENT:-}`, and a defaulted reference is invisible
  to the withhold gate. A BARE reference would withhold the plugin on
  every production install — the deadlock shape of ha-casa-app#429 — for
  a variable whose absence is the documented normal case. The default is
  EMPTY on purpose: `:-sandbox` would silently move a production install
  into the sandbox world.
- Any other value refuses every tool with one uniform sentence — an
  unrecognised mode never falls back to the real-money world.
- **A mode change on an existing install refuses, it does not migrate**
  (the `eb-environment` marker in the plugin data dir, plus an
  unconditional check for the other mode's ledger file). A different
  mode means a fresh install with its own data directory.

## What sandbox mode isolates

| Surface | Production | Sandbox |
|---|---|---|
| Enable Banking app | `casa-finance` (PRODUCTION) | `casa-finance-sandbox` (SANDBOX) |
| Vault items | `EnableBanking Key` / `EnableBanking` | `EnableBanking Key Sandbox` / `EnableBanking Sandbox` |
| Ledger | `bank_feed.sqlite` | `bank_feed.sandbox.sqlite` |
| API hosts | same (`api.enablebanking.com` / `enablebanking.com`) | same |

The names and hosts in that table are what the code uses; whether the provider
treats a sandbox application differently from a production one — activation in
particular — is an assumption, not something this commit shows.

Every tool response in sandbox mode is prefixed with a `[SANDBOX]`
banner, errors included. In BOTH modes a world guard verifies — before
any operation that addresses the application — that the wired app id
answers as the mode's own application (name + environment + id); a
`plugin-env.conf` copied from the other world's install refuses instead
of touching it.

## Playbook notes (read before writing/running plays)

- **Pin the install revision to `d432db0` or later** — earlier revisions
  have no sandbox mode.
- **`Mock ASPSP` cannot be linked, and that is not a plugin bug.** The
  precondition is in the code: the ledger keys accounts on
  `HMAC(IBAN, currency)`, so an account the provider returns without an IBAN has
  no key and linking refuses rather than inventing one. `Mock ASPSP` is assumed
  to be such a provider. Use a real-bank sandbox ASPSP for the link/read legs
  instead; if the one you pick also returns no IBAN, you will get the same
  refusal, which is the signal to try another.
- **Empty-vault runs work**: the sandbox credential item exists in no
  vault yet; the first store creates it (`opvault.upsert_field`,
  create-on-absent with two-negative evidence). The email sign-in dance
  is still one human copy/paste, once.
- The account is shared, so `GET /api/applications` is assumed to list the
  production app too. Sandbox reads that shared administrative metadata; the
  world guard is what stops it ever *addressing* the production app, items or
  ledger, and that guard is in the code rather than in the assumption.
- **Teardown** is playbook/operator-side by design: delete
  `casa-finance-sandbox` with the
  `DELETE /api/applications {"appId": …}` recipe and purge the two
  sandbox vault items. The plugin itself has no DELETE capability
  (`eb_admin.ALLOW`), in either mode. The plugin's protected
  `delete_all_data` revokes sandbox sessions and erases the sandbox
  ledger only (its DB *is* the sandbox file).
- A second `setup_bank_feed` on a healthy install is a verified no-op —
  the acceptance criterion the plays assert.
